# Website: source and build

[`site/build_site.py`](build_site.py) is the only source of the website. Never edit files in [`docs/`](../docs/) by hand except the images listed below; CI fails if [`docs/`](../docs/) differs from the build output.

## After a change
1. Text, layout, CSS or JS: edit [`site/build_site.py`](build_site.py), then run `python3 site/build_site.py`.
2. Score templates changed (cover, header line, footer): run `python3 site/make_previews.py`, then [`site/build_site.py`](build_site.py). It renders the example previews from the release packages (`ZIPS` in [`build_site.py`](build_site.py)) with the current templates: greyscale PNG, rendered straight from the PDF in five widths (160, 240, 320, 480, 720 px) for `srcset`, so the staff lines stay black and sharp at 1x, 2x and 3x (retina optimised; never shrink a big image).
2b. Example recordings changed (new example pack): `python3 site/make_web_audio.py <English example ZIP>` writes the 42 MP3s in `docs/audio/` (one set for both languages; needs ffmpeg).
3. Header image changed: see [`site/header/README.md`](header/README.md).
4. Always: `node site/render_test.js <out_dir>` (both languages, mobile 390, tablet portrait 820, tablet landscape 1180, desktop 1440). It must report `ok` everywhere; look at the screenshots.
5. Commit `site/` and [`docs/`](../docs/) together.

## Hosting (GitHub Pages)
The website is plain static HTML served straight from the repository: Settings, Pages, source **Deploy from a branch**, branch `main`, folder **`/docs`**. [`docs/.nojekyll`](../docs/.nojekyll) keeps GitHub from processing the files. Keep it that way:
- Do not switch the source to "GitHub Actions" and do not add a Pages or Jekyll workflow (for example the suggested "Deploy Jekyll with GitHub Pages dependencies preinstalled" from the Pages settings). Such a workflow runs on every push to `main`, builds the repository root and publishes the README instead of [`docs/`](../docs/); the site then shows the README in the Jekyll theme and `/en/` returns 404. This happened on 2026-10-31 and was fixed by deleting the workflow.
- With the source on "Deploy from a branch", the run "pages build and deployment" starts by itself after every push to `main`. If it does not appear, check the Pages settings first.

## Logo
`python3 site/logo/make_logo.py` draws the whole logo set. Source: the duck of the header image (group "duck" in [`site/header/header-src.svg`](header/header-src.svg)) as white lines plus an eighth note on red ground.
- **Seal logo** [`docs/img/logo.png`](../docs/img/logo.png) (144 px; header and README): printed like the impression of a Chinese stone seal (red fills almost the whole square, slightly uneven edge, uneven ink, pin holes). Transparent only in the thin margin outside the stone, the carved lines are opaque white, so it looks the same on light and dark pages.
- **Icons** [`docs/img/favicon.svg`](../docs/img/favicon.svg), `favicon-32.png`, [`docs/favicon.ico`](../docs/favicon.ico); [`docs/img/app-icon-1024.png`](../docs/img/app-icon-1024.png) (app stores, app screens), `favicon-180.png` (apple touch icon), `favicon-192.png`: one exact vector drawing, a flat red square to the very edge (no rounded corners, the operating system masks them), thick white lines, no texture; readable at 16 px. App icons keep more space around the drawing than the favicon (`INSET`).
Deterministic; `--seed N` changes the texture, `--preview FILE` writes a large preview . Needs numpy, scipy, pillow, cairosvg.

## Rules for the content
- Light / dark: the page follows the system setting; the button left of the language link (moon in light mode, sun in dark mode, drawn in the text colour: black or white) forces the other mode. The choice is kept in `localStorage` (`theme`), applied by a tiny script in the head before the first paint, and also switches the header image (`<picture>` source). 
- Section order: Start, Workflow, Practice (player, headphones, switches), Example (card with the fan of three score pages popping out of its top edge, title, size line and download button; below it the folder tree), Rights and AI, Licences. Numbers 01 to 05 in the headings follow it. The anchors are translated (`ids` in [`build_site.py`](build_site.py): German `#ablauf`, `#ueben`, `#beispiel-zip`, `#rechte-und-ki`, `#loslegen`, `#lizenz`; English `#workflow`, `#practice`, `#example-zip`, `#rights-and-ai`, `#get-started`, `#licence`); the menu has no GitHub icon.
- Footer (two lines, like the PDF and Markdown footers): `[GitHub mark, linked to the repo] choir-practice – KI-Musik-Workflow/-Skill für Claude.` and below it `[AI label, linked to the GitHub Pages site] <year> KI-generiert. Nutzung auf eigene Verantwortung.` (keys `foot_note`, `ai`, `foot_site`; year of the last release from `choir-practice/session-handoff.md`, so it changes with every release; PDF and Markdown carry the ISO date). Both marks have the same diameter (1.6 em); same size, body colour, no grey.
- Name of the site (next to the logo, page title, link preview): "Choir Practice Skill" in both languages (the same wordmark as the title of the READMEs). The skill itself is called "choir-practice" in every language, in the skill name, file names, repository and footers (not translated, also in German), always written out, no abbreviation. What is left of the old name (repository URLs): [`site/rename.md`](rename.md).
- Type: all running text 17 px (also the lead and descriptions), one smaller size 15 px only for labels, captions, controls and the footer, one larger size 22 px (plus the display sizes of h1, h2 and the key figures); no grey. Bold only for headings (also the folder names of the ZIP file), titles, numerals and the active menu item. Side margin 32 px on every screen size (`--gut`); the content is 1088 px wide at most (`--max` 1152 px minus the margins); header, content and footer share the same edges.
- Workflow: at most 12 steps; the tempo question belongs to Stop B, never a step of its own; shared steps read "Claude + Du".
- No call to install and no how-to instructions on the website or in the READMEs (owner's decision 2026-10-29): the project documents a private experiment. No "Get started" section, no install button, no `downloadUrl`.
- Licence section: PolyForm Noncommercial, link to the [`LICENSE.md`](../LICENSE.md) in the repo root.
- Example package (2/4, "Alle meine Entchen" / "All My Ducklings"): `python3 site/build_example.py de|en WORKROOT` builds it with the skill's own scripts (phases 3 to 7) from [`site/example/`](example/) (score, docs, session handoff per language) and writes the ZIP. Then `python3 site/make_web_audio.py <English ZIP>` (web recordings), `python3 site/make_previews.py --zip-dir DIR` (cover and page images), `python3 site/build_site.py`. The ZIPs go to the release; names are in `ZIPS` in [`build_site.py`](build_site.py).
- Album cover in the player ([`docs/img/cover-de.jpg`](../docs/img/cover-de.jpg), `cover-en.jpg`): `python3 site/make_player_covers.py` builds the cover of the example pack with the skill's own [`make_cover.py`](../choir-practice/scripts/make_cover.py). The example scores carry `"cover": {"color": "#d9251d"}` (the red of the website), so the hue comes from that colour and the cover inside the example package is the same red one; normal packs derive the hue from the key. Run it after any change to [`make_cover.py`](../choir-practice/scripts/make_cover.py), then `python3 site/make_web_audio.py --cover-only` (embeds the cover in the web recordings without touching the audio), then [`build_site.py`](build_site.py).

## Line breaks
No text block may end with a single word on its last line. `nobreak()` in [`build_site.py`](build_site.py) replaces the last space of every `p`, `li`, `h1` to `h4`, `figcaption`, `dd`, `dt`, `summary`, `label` (and of every line before a `<br>`, and of the footer spans) with `&nbsp;` at every build; texts that the page script sets use `nb()` in the script. New block elements or new script-set texts must be added there. Blocks with buttons or SVG are skipped on purpose.

## Cache busting
`bust()` in [`build_site.py`](build_site.py) appends `?v=<hash of the file>` to every `img/...` reference (src, srcset, preload, og:image) at every build. A changed image therefore gets a new URL; run [`make_previews.py`](make_previews.py) and [`build_site.py`](build_site.py) after any template change and the page shows the new example pages without a hard reload.
